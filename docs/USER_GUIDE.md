## Первая разблокировка

При первом открытии Web UI вместо привычного интерфейса появится экран **«Разблокировка
Marchi»** с одним полем — паролем. Это Master Key: единственный секрет, которым
защищено всё остальное (пароли IMAP-аккаунтов, OAuth2-токены, ключи S3). Введите пароль
от 12 символов — он будет задан как новый.

При каждом следующем запуске процесса (перезапуск контейнера, `systemctl restart`,
обновление) сервис снова стартует заблокированным, и тот же пароль его разблокирует.
Это не баг: пока сервис заблокирован, фоновая синхронизация не запускается — так короче
окно, в течение которого расшифрованные данные вообще существуют в памяти процесса.

Забытый пароль восстановить нельзя — это не «сброс через email», а ключ шифрования.
Единственный выход — начать с чистого `data_dir` (все ранее заархивированные письма при
этом останутся нечитаемыми, если не было отдельной резервной копии).

## Добавление почтового аккаунта

Раздел **Аккаунты** → форма «Добавить аккаунт»:

- **Email** и **IMAP-сервер** обязательны.
- **IMAP-порт**: можно оставить пустым — по умолчанию 993 для SSL/TLS, 143 для
  остальных режимов.
- **TLS**: `SSL/TLS` (implicit TLS, порт 993 по умолчанию) — стандартный выбор для
  большинства провайдеров; `STARTTLS` — для серверов, которые сначала принимают
  соединение в открытом виде и потом повышают его до TLS; «Без шифрования» — только
  для локальных тестовых серверов, никогда для реального почтового провайдера.
- **IMAP-логин**: если отличается от email (некоторые провайдеры это допускают).
- **IMAP-пароль**: для Gmail/Outlook с включённой двухфакторной аутентификацией — это
  почти всегда **пароль приложения** (app password), не основной пароль аккаунта; для
  них также доступна OAuth2-авторизация — см. [Настройки → OAuth2](#настройки).

После добавления нажмите **Проверить** в строке аккаунта — Marchi подключится и
покажет либо число найденных папок, либо текст ошибки сервера (неверный пароль,
недоступный хост, отказ TLS — сообщение от сервера показывается как есть).

Синхронизация запускается автоматически по расписанию (`sync.default_schedule` в
конфиге, по умолчанию — раз в 6 часов), а также вручную — кнопка **Синхронизировать**
на Dashboard рядом с аккаунтом.

## Правила архивации

Раздел **Правила**. По умолчанию, если правил нет — архивируется всё. Правило состоит
из:

- **Условий** — дерево из групп «ВСЕМ (И)» / «ЛЮБОМУ (ИЛИ)», вложенность до 3 уровней.
  Каждое условие — конкретный тип (домен отправителя, тема по regex, размер, дата,
  наличие вложений и т.д. — полный список в выпадающем списке добавления условия) плюс
  значение.
- **Действия**: `Архивировать`, `Пропустить` (не архивировать вовсе), `Архивировать и
  удалить с сервера`, `Архивировать и отметить прочитанным`.
- **Приоритета** — правила проверяются сверху вниз, побеждает первое совпавшее. Порядок
  меняется перетаскиванием строки за маркер `⛿` слева.

Правила можно вести и в виде файла — `rules.yaml` в `data_dir`, если он существует,
Marchi следит за изменениями и однонаправленно синхронизирует его содержимое в БД
(изменения через Web UI обратно в файл не пишутся — редактируйте что-то одно).

Перед сохранением правило можно проверить на уже заархивированной почте — кнопка
**«Проверить на архиве»** в форме создания/редактирования правила показывает, сколько
писем из архива совпало бы с текущим деревом условий (и до 20 примеров), не сохраняя
само правило и никак не меняя архив. Особенно полезно перед сохранением правила с
действием `archive_and_delete` — прежде чем правило начнёт реально удалять письма с
сервера, стоит убедиться, что оно матчит именно то, что задумано.

В списке правил у каждого — столбец статистики: сколько раз правило сработало за всё
время и дата последнего срабатывания («Никогда» — если ещё ни разу). Счётчик
накапливается при каждой синхронизации и не сбрасывается при редактировании условий
правила.

## Архив: поиск, просмотр, скачивание

Раздел **Архив**. Слева — дерево «аккаунт → папки» для фильтрации по конкретному
источнику; сверху — форма поиска (текст, диапазон дат, наличие вложений, сортировка по
релевантности или дате). На узких экранах (телефон, планшет в портретной ориентации)
результаты показываются карточками вместо таблицы — тот же набор действий и полей,
просто в вертикальной раскладке.

В результатах у писем, физически хранящихся в S3 (а не локально), — бейдж **S3**. Клик
по теме письма открывает просмотр: заголовки, тело (HTML — санитизировано, безопасно
для просмотра; если HTML недоступен — текстовая версия), вложения отдельными ссылками,
кнопка «Скачать .eml» (оригинальный файл письма байт-в-байт) и кнопка **«Удалить из
архива»** — безвозвратно удаляет письмо (локальный файл, S3-копию если есть, запись в
поисковом индексе) после подтверждения; в отличие от правил `archive_and_delete`
(которые решают, архивировать ли письмо при синхронизации), это ручное удаление уже
заархивированного письма — например, случайно заведённого дубликата. Если письмо
хранится только в S3, тело подгружается на лету при открытии — незаметно для
пользователя, но может занять секунду-две при первом просмотре после долгого хранения
в S3.

## Восстановление писем

В том же разделе **Архив**, над результатами поиска — чекбоксы у каждого письма плюс
выбор целевого аккаунта и папки. Отметьте нужные письма, выберите, куда восстанавливать,
нажмите **Восстановить выбранное**. Прогресс — в реальном времени рядом с кнопкой.

Технически восстановление — это IMAP `APPEND` в целевую папку; если по какой-то причине
это невозможно (сервер не поддерживает нужную команду и т.п.), автоматически
используется SMTP-отправка как резервный способ. История восстановлений для каждого
письма видна в его собственном окне просмотра — метод (`imap_append`/`smtp`), статус,
дата.

Если нужно восстановить не отдельные найденные письма, а весь аккаунт или целиком одну
папку — не обязательно сначала находить их поиском. При открытом конкретном аккаунте
(и, если нужно, папке) в Архиве появляется отдельная панель: выбираете целевой аккаунт,
вписываете корневую целевую папку и жмёте **«Восстановить эту папку»** или
**«Восстановить весь ящик»**. При восстановлении всего ящика структура исходных папок
сохраняется — каждая исходная папка попадает в свою подпапку под указанным корнем;
при восстановлении одной папки все письма кладутся прямо в корень. Здесь же можно
опционально сузить восстанавливаемые письма диапазоном дат («Дата с»/«Дата по») — без
дат восстанавливается вся папка/весь аккаунт. Оба варианта требуют подтверждения — это
необратимо создаёт письма на живом IMAP-сервере.

## Массовые операции над результатами поиска

Те же чекбоксы у результатов поиска, что используются для восстановления, работают и
для двух других операций, синхронных (без прогресс-бара — результат виден сразу):

- **Удалить выбранные** — безвозвратно удаляет отмеченные письма из архива (то же, что
  кнопка «Удалить из архива» в просмотре одного письма, но сразу для нескольких).
- **Переместить выбранные** — переносит отмеченные письма в другую папку в рамках того
  же аккаунта (перенос между разными аккаунтами не поддерживается — папка привязана к
  конкретному аккаунту). Если папки с таким именем ещё нет — она создаётся; если уже
  есть и активно синхронизируется с реальным сервером — её собственная синхронизация
  этим переносом не затрагивается.

Обе операции — по подтверждению, применяются только к отмеченным чекбоксом письмам.
Результат («N перемещено/удалено, M не удалось») появляется рядом с кнопками, страница
обновляется, чтобы список результатов больше не показывал уже удалённые/перемещённые
письма.

Отдельно — **экспорт**: `POST /api/v1/export` (пока без кнопки в Web UI, только через
REST) забирает выбранные письма или весь результат поискового запроса и отдаёт их
единым `.zip` (по файлу `.eml` на письмо, с сохранением структуры
аккаунт/папка/год-месяц) либо одним файлом `mbox` — что удобнее для последующего
`marchi import` в другой архив или сторонний почтовый клиент. Подробности и формат
запроса — [docs/api/openapi.yaml](api/openapi.yaml).

## Импорт почты

Перенос уже существующей почты (архив другого инструмента, экспорт из старого ящика)
внутрь Marchi — без браузера, через CLI:

```bash
marchi import --type mbox --path /path/to/archive.mbox --as-account old-mail@example.com
marchi import --type maildir --path /path/to/Maildir --as-account old-mail@example.com
marchi import --type eml --path /path/to/emails/ --as-account old-mail@example.com
```

`--as-account` — email, под которым импортированные письма появятся в Archive/Dashboard;
если аккаунта с таким email ещё нет, он создаётся автоматически (неактивным, без
реальных IMAP-настроек — только для группировки импортированных писем, никогда не
пытается подключиться к серверу). Импорт идемпотентен: дедупликация — по Message-ID,
так что повторный запуск на том же источнике (или на источнике с несколькими новыми
письмами, дописанными с прошлого раза) заново заархивирует только то, чего ещё нет в
архиве. Правила архивации к импорту не применяются — переносится всё как есть.

## Настройки

Раздел **Настройки**:

- **Master Key** — смена пароля. Ничего заново не шифруется: меняется только обёртка
  ключа шифрования на диске, все уже сохранённые пароли/токены/письма в S3 остаются
  читаемыми новым паролем без каких-либо дополнительных действий.
- **Хранилище S3** — эндпоинт, регион, бакет, ключи доступа. Path-style адресация нужна
  почти всегда для MinIO и self-hosted S3-совместимых хранилищ (не для настоящего AWS
  S3). «Проверить подключение» делает безопасную read-only проверку доступности бакета,
  ничего не создавая и не загружая.
- **Приложения OAuth2 (свои)** — Marchi не поставляет общий OAuth2-клиент: нужно
  зарегистрировать своё приложение в Google Cloud Console / Azure Portal и вписать сюда
  `Client ID`/`Client secret`/`Redirect URL`.
- **Уведомления** — webhook (URL + секрет для HMAC-подписи тела запроса) и/или email
  через отдельный исходящий SMTP-relay (не тот же аккаунт, что используется для
  восстановления). Срабатывают при сбое синхронизации или retention, росте очереди
  загрузки в S3 и нехватке места на диске; повторные срабатывания одного и того же
  события подряд гасятся (не чаще раза в час), чтобы не заспамить один и тот же сбой.
  Кнопка «Отправить тестовое уведомление» проверяет канал отдельно, не дожидаясь
  реального сбоя.
- **Аудит-лог** — последние 50 записей: разблокировки веб-сессий, создание/изменение/
  удаление правил, восстановление (одиночное и массовое), удаление писем — с временем и
  IP-адресом источника запроса (CLI-события — без IP).
- **Retention по умолчанию** — три числа в днях: сколько письмо живёт локально до
  переноса в S3, через сколько дней после архивации оно физически переносится в S3, и
  через сколько дней после этого удаляется окончательно (из S3 и из БД). Пустое поле —
  «никогда». Действует для всех аккаунтов, у которых нет собственного переопределения;
  сами retention-проходы запускаются ежедневно автоматически (а также вручную —
  `marchi retention run`).
- **Поисковый индекс** — «Пересобрать индекс» полностью переиндексирует архив с нуля из
  уже сохранённых `.eml`-файлов и метаданных в БД. Нужно редко: если индекс подозревается
  в рассинхроне (например, после восстановления из бэкапа без индекса) или после ручного
  вмешательства в `maildir/`.
- **Последние синхронизации** — журнал последних прогонов по всем аккаунтам: сколько
  писем обработано/заархивировано, сколько ошибок, статус.

## Тема и язык интерфейса

Кнопка в правом верхнем углу переключает тёмную/светлую тему (по умолчанию — как в
системных настройках браузера), выбор запоминается в cookie. Рядом — переключатель
`EN`/`RU`, тоже переживает перезагрузку страницы и не требует повторного входа.

## CLI-эквиваленты

Всё, что можно сделать в Web UI, частично доступно и без браузера — полезно для
скриптов и unattended-сценариев:

```bash
marchi add-account user@example.com --host imap.example.com --tls ssl
marchi list-accounts
marchi test-connection user@example.com --host imap.example.com
marchi sync user@example.com
marchi status                    # история синхронизаций по всем аккаунтам
marchi retention run             # один проход retention прямо сейчас
marchi reindex                   # пересборка поискового индекса
marchi backup run <dest-dir>     # горячий бэкап БД+maildir+ключей, без остановки сервиса
marchi backup verify <dest-dir>  # сверка контрольных сумм и целостности бэкапа
marchi config show               # итоговая конфигурация (дефолты + файл + окружение)
```

Подробности про `backup`/`backup verify` (что именно копируется, как восстанавливать) —
в README, раздел «Резервное копирование и восстановление».

`marchi --help` и `marchi <команда> --help` уважают `--lang ru` (или переменную
окружения `LANG`/`LC_ALL`) — описания команд переключаются на русский так же, как и
Web UI.

## Политика 0.x и совместимость

Marchi ещё не прошёл security-аудит третьей стороной и не имеет широкой базы внешних
пользователей — версия `0.x` (semver) честно об этом сигнализирует: **между минорными
версиями (`0.4.0` → `0.5.0`) возможны обратно несовместимые изменения** — формата
`config.yaml`, схемы БД (миграции всегда идут вперёд, отката на предыдущую минорную
версию после апгрейда не гарантируется), REST API. Патч-версии (`0.6.0` → `0.6.1`) таких
изменений не несут.

Практический вывод: перед апгрейдом на новую минорную версию — прочитать
[CHANGELOG.md](../CHANGELOG.md) за неё, и снять [бэкап](../README.md#резервное-копирование-и-восстановление)
(`marchi backup run`), если апгрейд происходит не на копии для тестирования.

### Измеренные ориентиры

Числа ниже — из одного прогона на разработческой машине (Apple Silicon, локальный
Dovecot в Docker на том же хосте — то есть сетевая задержка практически нулевая; синхронизация
через реальный интернет к внешнему IMAP-серверу будет медленнее, узкое место сместится с
CPU/диска на сеть и сам IMAP-сервер) — это ориентир порядка величины, не гарантированный
SLA и не результат формального бенчмарка на выделенном стенде.

| Операция | Объём | Результат |
|---|---|---|
| `marchi sync` (первичная архивация) | 2000 писем, ~1.2 КБ тела каждое | ~48 с (≈42 писем/с) |
| `marchi reindex` (полная переиндексация) | те же 2000 писем | ~33 с (≈60 писем/с) |
| Место на диске: Maildir (`.eml`) | 2000 писем | ~7.8 МБ (≈3.9 КБ/письмо) |
| Место на диске: SQLite (метаданные) | 2000 писем | ~2.0 МБ (≈1 КБ/письмо) |
| Место на диске: поисковый индекс (Bluge) | 2000 писем | ~5.3 МБ (≈2.65 КБ/письмо) |

Итого — на 2000 писем без вложений уходит ≈15 МБ (Maildir + БД + индекс), и это растёт
линейно с числом писем (SQLite/Bluge не имеют доп. плато с ростом объёма при таких
масштабах). Вложения хранятся отдельно от этого расчёта — их объём зависит от почты
целиком и не оценивался отдельно.
